# 審查範圍與執行效率

本文件約束準備代理、協調代理與 reviewer。流程同步的實際交付門檻仍由 [flow-docs-sync.md](flow-docs-sync.md) 定義。

## 先用工具決定範圍

審查前以實際比較基準執行 `flow_checker.py impact --root . --base <BASE>`，保存輸出的候選、指紋與範圍。`review_required` 為空時不派 reviewer；重用 `review_reused` 的證據，`unaffected` 不重審。AST 相同的格式與一般註解變更直接略過 AI 重審；CI 不要求為此補改快照，impact 以 `byte_only_sources` 揭露實際位元組差異。需要重新整理來源摘要時才執行 snapshot，不重畫流程。不同 AST 不等於已證明行為不同，仍須依影響判斷。

`python`、`tree-sitter` 是符號模式；`python-module`、`tree-sitter-module` 是整模組 AST 模式。字串、裝飾器、工具指令等輸入保留於語意比較。解析失敗必須修正或明示改用保守模式，不能當作沒有變更。`file` 僅供尚未支援的格式，按位元組比較並在 impact 的 `raw_fallbacks` 揭露。

區分 `changed_source_content`、`changed_source_modes` 與 `changed_policy_inputs`。來源內容未變而只有模式或政策改動時，核對遷移與政策，引用原內容的有效審查；不為此重新閱讀整份應用程式。必要的上下文由 reviewer 依疑點增讀並說明原因。

## 凍結候選與集中審查

程式、流程、政策與測試穩定且機械檢查完成後，提交候選並派審查；審查期間凍結這些輸入。審查證據可於其後加入。輸入再次變更時重算 impact，只重審失效範圍。

共用依賴由同一位 reviewer 讀取一次。高度重疊的功能集中成一份審查任務，逐功能回傳各自的指紋與結論；獨立實作者不能審查自己的成果。不同 reviewer 不分別重讀相同的共用政策與模組。初次審查應一次盤點成功、失敗、重試、暫停、取消、發布與清理的實際分支，回報全部可證實的發現。

會誤導狀態、副作用、檔案歸屬或失敗恢復的問題列為阻擋。純措辭、偏好及範圍外改善列為建議，不讓它們反覆阻擋交付。重審只檢查修正及其必要相鄰影響，沿用未失效的結論。

兩輪修正／重審仍有問題時，由協調代理在同一任務內先完成整體分支核對，再對剩餘範圍安排獨立審查；不以輪次數要求使用者重新授權，也不略過未完成的審查門檻。這是本專案對一般技能輪次限制的明確交付規則。

## Reviewer 的 token 使用

派工包只含工作目錄、比較基準、候選提交、impact 清單、變更輸入、有效證據索引與已執行測試，不傳入整段工作對話。先報出預計閱讀的新增範圍，再按疑點擴充；相同內容已在本輪上下文中時不再次讀取。

審查結果除功能、指紋、判定與發現外，記錄 `newly_read_paths`、`reused_evidence`、`additional_reads` 及原因。執行環境提供實際 token 用量時記錄來源與數值；否則 `token_usage` 明示 `unavailable`，不得把估算或節省量當成實測。節省 token 不能代替必要的來源或資料安全查核。

## 代理交接與等待

交接固定提供唯一工作目錄、基準、候選提交、已驗證的 Python／測試環境、測試命令及未完成項目。優先使用已驗證且符合依賴的環境，僅補缺少的依賴；不把同一份變更複製回另一個工作區形成第二份未提交內容。

CI、審查與合併使用既有 watcher 集中觀察，後續動作依最終狀態。進度訊息以階段變化、失敗或阻礙為主。交付後核對遠端 PR、主分支與本機工作區狀態，保留無關改動並明示尚未同步的項目。
